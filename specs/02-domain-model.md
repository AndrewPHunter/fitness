# 02 — Domain Model

All types in this document are normative. Field names are part of the contract.

## 2.1 Entity overview

```
Program (immutable once stored)
 ├── ExerciseDefinition[]      canonical exercise declarations
 ├── Session[]
 │    └── Block[]              single | superset
 │         └── ExerciseEntry[] the prescription
 ├── Schedule                  rotation | weekdays
 └── FrequencyTarget[]         optional, display-only

SessionLog (append-only in practice, editable by the user)
 └── SetLog[]                  the actual performance
```

## 2.2 Identity rules

Identity is the highest-risk area of this model. Read this section carefully.

### `exerciseId` — the load-bearing identifier

`exerciseId` is a stable slug (`^[a-z0-9]+(-[a-z0-9]+)*$`) that identifies an exercise
**across programs**, not just within one.

This matters because the app's most valuable feature — *"what did I lift for this last time?"* —
works by looking up prior `SetLog`s by `exerciseId`. If two programs refer to the same physical
movement using different identifiers, that history silently splits in two.

Therefore:

- `exerciseId` is **required** and must match the slug pattern. Free-text names are not identity.
- Display names are **not** identity. Two programs may render `barbell-back-squat` as
  "Back Squat" and "Squat" — history still unifies.
- The application maintains a **local exercise index** built from every program ever uploaded.
- On upload, the app **reports** which `exerciseId`s are already known and which are new. This
  is informational and must reflect real index state — it is not a validation step and must not
  block the upload.
- Reconciling two ids that turn out to mean the same movement is [EXT-6](01-product-spec.md),
  not Core.

The authoring prompt pack instructs the LLM to reuse canonical slugs. The schema deliberately
does **not** enforce membership of a closed registry — that would make it impossible to author
programs containing unusual exercises.

### Other identifiers

| Field | Scope | Rule |
|---|---|---|
| `programId` | Global | Slug, declared in the file. Identifies the program across versions. |
| `version` | Per program | Integer ≥ 1, declared in the file. `(programId, version)` is unique. |
| `sessionId` | Within a program | Slug. Referenced by `schedule`. |
| `sessionLogId` | Global | Generated by the app via the injected id provider. |
| `setLogId` | Global | Generated by the app via the injected id provider. |

## 2.3 Program

Immutable once stored. Re-uploading a file whose `(programId, version)` already exists is
rejected as a duplicate. Re-uploading with an incremented `version` stores a **new, separate**
program record; the previous version and all history logged against it are retained unchanged.

```ts
interface Program {
  programId: string;              // slug
  version: number;                // integer >= 1
  name: string;
  description?: string;
  exercises: ExerciseDefinition[];
  sessions: Session[];
  schedule: Schedule;
  frequencyTargets?: FrequencyTarget[];
}

interface ExerciseDefinition {
  exerciseId: string;             // slug — see 2.2
  name: string;                   // display only
  notes?: string;
}
```

## 2.4 Session and Block

```ts
interface Session {
  sessionId: string;              // slug, unique within the program
  name: string;
  notes?: string;
  blocks: Block[];                // ordered; execution order
}

type Block =
  | { type: 'single';   entry: ExerciseEntry }
  | { type: 'superset'; entries: ExerciseEntry[] };   // 2..8 entries
```

A **superset** is a group of exercises performed back-to-back before resting. Its only
behavioural consequence is in the UI: [06](06-ui-ux.md) requires the grouped entries to be
logged in round-robin order rather than one exercise at a time.

Supersets do not nest. A `superset` block contains only `ExerciseEntry`, never another `Block`.

## 2.5 ExerciseEntry — the prescription

```ts
interface ExerciseEntry {
  exerciseId: string;             // must resolve against Program.exercises
  sets: number;                   // integer 1..20
  reps: number;                   // integer 1..100 — a fixed number, never a range
  targetWeight?: Load;            // display-only intent
  targetRpe?: number;             // 1..10 in 0.5 steps — display-only intent
  restSeconds?: number;           // integer 0..600
  notes?: string;
}

interface Load {
  value: number;                  // > 0
  unit: 'kg' | 'lb';
}
```

Every set within one entry shares the same prescribed `reps`. Ramping loads and per-set
variation are out of scope ([01 §1.5](01-product-spec.md)).

`targetWeight` and `targetRpe` are governed by [C9](00-constitution.md): displayed, never
enforced.

## 2.6 Schedule

A discriminated union on `mode`. Both modes are Core.

```ts
type Schedule =
  | { mode: 'rotation'; sequence: string[] }                    // sessionIds, length 1..60
  | { mode: 'weekdays'; days: Partial<Record<Weekday, string>> } // sessionId per day

type Weekday = 'mon'|'tue'|'wed'|'thu'|'fri'|'sat'|'sun';
```

### `rotation`

An ordered list of `sessionId`s. The same `sessionId` may appear multiple times — this is the
mechanism by which frequency is expressed (see §2.7).

**Next-session rule:** the next session is `sequence[(completedCount) mod sequence.length]`,
where `completedCount` is the number of completed `SessionLog`s recorded against this
`(programId, version)`. The sequence wraps indefinitely.

The rotation is **not** anchored to the calendar. It advances only when a session is completed.
Skipping a real-world day has no effect on position.

### `weekdays`

Sessions pinned to days of the week. Days absent from `days` are rest days.

**Next-session rule:** the session mapped to today's weekday, using the injected clock and
timezone. If today is a rest day, the app displays the next upcoming training day and its
session. The app does **not** track, flag, or penalise missed days.

## 2.7 Frequency: expressed structurally, displayed honestly

The user's real program trains on an **every-other-day cadence** — which drifts against the
calendar — while needing some exercises roughly 3×/week and others roughly 1×/week.

This is expressed **entirely within the rotation sequence**, at authoring time. Every other day
yields 7 sessions per 14 days. An exercise appearing in 6 of those 7 sessions occurs
6/14 days ≈ 3×/week; one appearing in 2 of 7 occurs ≈ 1×/week.

**The application performs no scheduling arithmetic to achieve this.** The LLM does the
arithmetic once, when authoring. The app just walks the sequence.

### The honest limitation

A rotation delivers the correct **average** frequency, not a per-calendar-week guarantee. In any
given week an exercise may land 3 or 4 times. This is accepted and must not be concealed.

### `frequencyTargets` — declared intent

```ts
interface FrequencyTarget {
  exerciseId: string;             // must resolve against Program.exercises
  perWeek: number;                // > 0, may be fractional
}
```

Governed by [C9](00-constitution.md). These are **authoring intent for display only**. The
application must not validate the sequence against them, must not warn when observed frequency
diverges, and must not adjust anything.

### Observed frequency — CORE-7

The app computes, from **actual logged session dates**, the number of times each exercise was
performed in the trailing 7 and 14 days, and displays it alongside the declared target where one
exists.

- Windows are computed against the injected clock, inclusive of today.
- The calculation is a pure function of `(SetLog[], now)`.
- Where no `frequencyTarget` is declared, observed frequency is shown without a target.

## 2.8 Logged data

```ts
interface SessionLog {
  sessionLogId: string;
  programId: string;
  programVersion: number;         // binds history to the exact version — C3
  sessionId: string;
  startedAt: string;              // ISO 8601 with offset
  completedAt: string | null;     // null while in progress
  setLogs: SetLog[];
  notes?: string;
}

interface SetLog {
  setLogId: string;
  exerciseId: string;
  blockIndex: number;             // position within Session.blocks
  entryIndex: number;             // position within the block's entries; 0 for 'single'
  setIndex: number;               // 0-based, within the entry
  weight: Load;                   // ACTUAL — see 2.9
  reps: number;                   // ACTUAL, integer >= 0
  rpe: number | null;             // ACTUAL, 1..10 in 0.5 steps, or null if not recorded
  loggedAt: string;               // ISO 8601 with offset
}
```

`completedAt === null` marks a session in progress. Only sessions with a non-null `completedAt`
advance the rotation (§2.6).

## 2.9 Units: stored, never converted

`Load` carries its own `unit`. **Stored values are never converted.**

A set logged as `{ value: 100, unit: 'kg' }` is stored, exported, and re-imported as exactly
that, forever. Converting on write would introduce floating-point drift and silently corrupt
history over time — a direct violation of [C3](00-constitution.md).

- A global setting selects the **default unit for new input**.
- Changing that setting affects **future input only**. It must not rewrite stored data.
- Display-time conversion is permitted, provided the stored value is unchanged and the UI makes
  clear which unit was originally recorded.

## 2.10 Weight prefill — CORE-5

When rendering a weight input for an exercise, the default value is the `weight` of the
**most recent `SetLog` for that `exerciseId`**, by `loggedAt`, across **all** programs and
versions.

- Lookup is by `exerciseId` alone — not by program, session, or set position.
- If no prior log exists, the field falls back to `targetWeight` if the entry declares one,
  and is otherwise empty.
- The prefilled value is always editable, and prefilling never writes anything on its own.
- The UI must distinguish a prefilled default from a value the user has confirmed. An untouched
  prefill must not be recorded as a logged set.
