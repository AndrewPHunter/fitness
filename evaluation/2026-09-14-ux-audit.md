| Trigger       | The owner's first real use surfaced three problems that five graded rounds did not |
| Build audited | `956832d` (iteration 5), live at `andrewphunter.github.io/fitness/`                |

| Author        | Claude Opus 5                                                                      |

## 1. Why the graded rounds missed this

Every UX criterion across rounds 1–5 was verified by **DOM inspection**: setting values in script,
reading `innerText`, navigating with `location.hash`. That method checks that text _exists in the
page_. It cannot see whether a person sees it.

All three problems the owner reported are invisible to that method:

| Owner's report                          | Why DOM inspection missed it                                                           |
| --------------------------------------- | -------------------------------------------------------------------------------------- |
| Saves don't indicate they worked        | `"Set 1 saved."` is in the DOM — inside a screen-reader-only element                   |
| Validate, then scroll to see the result | `innerText` returns the preview regardless of scroll position                          |
| After Activate, unclear where to start  | Grading jumped to Today with `location.hash`, bypassing the discovery problem entirely |

**Scores for rounds 1–5 stand**, because they were graded against the rubric as written, and the
rubric contained no requirement for visible feedback, scroll or focus management, or next-step
navigation. But every UX pass in those records should be read as _"present in the DOM"_, not
_"perceivable by a user"_.

The specification contributed directly. [06 §6.2](../specs/06-ui-ux.md) **UX-8** requires that
_"all state changes [are] announced to assistive tech via appropriate roles or live regions."_ The
implementation satisfied that literally, with a single screen-reader-only region — and no
requirement anywhere asked for a visible equivalent.

## 2. Method this time

Every flow walked as a first-time user, navigating **only** through controls a user can see and
tap. At each step, measured rather than inferred:

- whether the result of the action sits inside the **usable viewport** — below the top of the
  screen and above the fixed bottom nav, which begins at **779 px**
- whether a control had to be scrolled to before it could be tapped, and how far
- where focus lands after the action
- how long feedback persists
- the number of taps from one step to the next

**Limitation.** The session was not open in a window, so the Browser pane could not composite
frames and no screenshots were possible. Geometry is exact; _visual weight and hierarchy_ are not
assessed here (§7).

## 3. Root causes

Four systemic causes account for nearly every finding below.

### RC-1 — Action feedback is screen-reader-only (P0)

The app's single status region is `div.visually-hidden`: `1px × 1px`, `clip: rect(0,0,0,0)`,
`clip-path: inset(50%)`. Every confirmation is written there and **nowhere else**:

`Every Other Day Strength v1 saved.` · `Active program saved.` · `Session start saved.` ·
`Set 1 saved.` · `Completed session saved.` · `Set correction saved.` · `Settings saved.`

After tapping **Log set**, the only sighted-visible text anywhere on screen matching
_saved / logged / ✓_ is an instruction (_"Confirm it with Log set"_), a field label, and a
**Saved sets** heading and ✓ that are both below the fold.

The one exception is the Author screen's **Copy personalized prompt**, whose confirmation is a
separate visible element rendered **directly below the button** (471 px → 551 px). It is the only
action in the app whose feedback a sighted user sees, and it is the pattern to replicate.

### RC-2 — Results render far from the action, with no scroll or focus management (P0)

Long single-column pages place the outcome of an action hundreds of pixels below the control that
triggered it, and nothing moves the user there.

### RC-3 — No next step after a state change (P0)

Changing state never offers what to do next. The clearest case is activation (F-3).

### RC-4 — Screens are ordered by feature, not by task (P1)

`#/programs` is **1,752 px** tall empty (2.1 screens) and **2,324 px** with a preview. The first-run
user's actual first step is below the fold.

| ------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **F-1** | **Log set produces no visible confirmation** _(owner report 1)_                  | After tapping: prescription header unchanged (`3 sets × 5 reps`); weight and reps unchanged (`100`, `5` — prefilled from the set just logged); confirmation screen-reader-only; the new saved row appears at **752 px**, 27 px above the nav; the only other change is `0/12` → `1/12` in small text. The screen looks almost identical before and after. Mid-workout this invites double-logging, or distrust of the log |
| **F-2** | **Validate result is off-screen — success and failure alike** _(owner report 2)_ | Preview at **1,212 px**; error list at **1,187 px**; usable viewport ends at 779 px; focus stays in the textarea. The errors are real but unobservable without scrolling — failure that is not visible in practice sits uncomfortably close to [C1](../specs/00-constitution.md)                                                             |
| **F-3** | **After Activate there is no way to start** _(owner report 3)_                   | No **Start session** anywhere on `#/programs`, nor on the program detail page, whose only non-nav action is a disabled _"Currently active"_. Confirmation is screen-reader-only. The sole route is already knowing to tap **Today** in the nav                                                                                                                                                                            |

## 5. What works

Recorded so a fix does not break it.

- **Today → Start session** is in view, and **Complete** lands back on Today with the next session ready
- **Resume** is clear: _"Pick up where you left off"_ with the action in view
- **Superset round-robin** runs in the correct order in practice
- **Delete confirmation** copy is specific and honest — it names the exact set and date
- **Author → Copy** shows its confirmation directly below the button — the model for RC-1
- History exercises are tappable and in view; nav targets are 62 px wide

## 6. Recommended direction

Not a specification — input for one.

1. **Visible, anchored feedback for every state change**, adjacent to or replacing the control
   that triggered it, _in addition to_ the screen-reader region, never instead of it. For Log set:
   a clear `✓ Set 1 · 100 kg × 5` in view, the header advancing to `Set 2 of 3`, and the saved row
   appearing where the eye already is.
2. **Move focus and scroll to the result** after Validate — the preview or the error summary —
   with **Import** in the preview's header.
3. **Offer the next step** after every state change: activation offers _"Start A — Squat /
   Bench"_.
4. **Order screens by task.** First run leads with getting the prompt, not an empty paste box.
5. **Discard** for a session with zero logged sets.
6. **Keep Log set reachable while typing**, measured against the visual viewport.
7. **Clear stale notices on navigation**, so a visible notice never follows the user onto an
   unrelated screen.
8. Fix dialog focus and the run-together link names.

### A grading change, not only a product change

Whatever specifies this must be verifiable by **what is perceivable**, not what is in the DOM.
Playwright's `toBeInViewport()` makes that checkable in CI: assert the confirmation is in the
viewport after each action, rather than that its text exists somewhere in the page.
